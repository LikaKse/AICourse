# День 11. Модель памяти ассистента

Агент на Gemini (`gemini-3.5-flash-lite`, как в Днях 8–10) с явной моделью памяти из трёх независимых
слоёв: **краткосрочная**, **рабочая** и **долговременная**. Проект создан на основе архитектуры `gemini-task10`.
Исходные проекты не изменялись. `.env`, виртуальное окружение, результаты и состояние Дня 10 не копировались.

| Слой | Что хранит | Файл | Кто пишет | Что читается в промпт |
|---|---|---|---|---|
| **Short-term** | история текущего диалога | `short_term.json` | код, без LLM | последние `SHORT_TERM_WINDOW` сообщений |
| **Working** | текущая задача: цель, ограничения, промежуточные результаты, статус | `working_memory.json` | менеджер памяти (LLM) + проверки кода | вся задача, если она активна (`status ≠ done`) |
| **Long-term** | профиль, устойчивые предпочтения, решения, знания (Sticky Facts Дня 10) | `long_term.json` | менеджер памяти (LLM) + проверки кода | все факты, сгруппированные по виду записи |

## Запуск

```bash
cd gemini-task11
../venv/bin/python -m pytest -q                        # 89 тестов, всё офлайн
../venv/bin/python main.py --dry-run                   # правила, данные, прогноз вызовов и цены (без API)
../venv/bin/python main.py --offline-experiment        # эксперимент на FakeClient → results/offline/
../venv/bin/python main.py --experiment                # эксперимент на Gemini → results/gemini/ (ПЛАТНО, спросит y/N)
../venv/bin/python main.py --report offline            # пересобрать report.md из experiment.json
../venv/bin/python main.py --chat [--offline]          # чат с памятью в state/ (--offline — FakeClient)
```

Общие флаги: `--window N` (окно краткосрочной памяти), `--results-dir`, `--state-dir`, `--overwrite`.
Если результаты уже есть, без `--overwrite` они не перезаписываются. Это проверяется до первого платного вызова.

Команды чата:
- `/memory` — содержимое всех слоёв;
- `/prompt` — что уйдёт в модель;
- `/rules` — правила записи и чтения;
- `/clear short|working|long|all` — очистить слой;
- `/task done` — завершить задачу;
- `/exit` — выход.

## Архитектура

```
gemini-task11/
├── config.py               # модель, тарифы, окно, флаги чтения, системные инструкции
├── agent.py                # Agent: update_memory() (1 вызов на сообщение), ask(), token_breakdown()
├── memory/
│   ├── base.py             # MemoryLayer: load / save / clear / prompt_contents / stats; PromptBlock
│   ├── storage.py          # заголовок файла {format_version, layer, saved_at}, атомарная запись
│   ├── rules.py            # ЯВНЫЕ правила записи и чтения (таблицы + исполняемые check_*)
│   ├── evidence.py         # проверка цитат и чисел (из Дня 10) + «вопрос — не факт»
│   ├── short_term.py       # ShortTermMemory
│   ├── working.py          # WorkingMemory (TaskState, архив завершённых задач)
│   ├── long_term_store.py  # Fact / FactsState / apply — перенесённый facts_store Дня 10
│   ├── long_term.py        # LongTermMemory + render_facts
│   └── manager.py          # MemoryManager: маршрутизация операций, порядок промпта, clear(layer)
├── experiments.py          # единый сценарий, 4 варианта очистки, токены по слоям, report.md
├── fake_client.py          # FakeClient, scripted_extractor, echo_responder
├── main.py                 # CLI
├── data/                   # scenario.json, questions.json, expected.json, offline_extraction.json
├── results/offline/        # experiment.json, report.md, state/ (файлы слоёв каждого варианта)
└── tests/                  # pytest
```

**Разделение слоёв.**
- Каждый слой — отдельный класс со своим файлом.
- В заголовке файла есть поле `layer`. Файл одного слоя нельзя загрузить в другой: будет `MemoryLoadError`.
- Слои ничего не знают друг о друге. Связывает их только `MemoryManager`.
- `clear(layer)` переписывает ровно один файл. Тест сравнивает SHA-256 всех трёх файлов до и после.
- При создании `MemoryManager` загружает три файла. Это и есть восстановление после перезапуска.

**Один вопрос пользователя** (`Agent.ask`, `remember=True`):

```
update_memory(вопрос)   ← 1 вызов Gemini «менеджер памяти» (JSON Schema): операции для working / long_term
                          код проверяет каждую по правилам rules.py и пишет в файл своего слоя
prompt_blocks()         ← правила чтения: [LT] → [WM, если задача активна] → [последние N сообщений]
count_tokens × 5        ← LT, WM, ST, вопрос, весь промпт — отдельно (бесплатно)
generate_content        ← ответ; usage_metadata — фактические токены
record_exchange         ← краткосрочная память: только успешная пара
```

Контрольные вопросы (`remember=False`) память не меняют. Тест проверяет, что файлы после вопросов побайтово те же.

## Перенос Sticky Facts в долговременную память

`memory/long_term_store.py` — это `facts_store.py` Дня 10.

**Перенесено без изменений:**
- формат `Fact`: `key, value, kind, category, evidence, source_message, proposal_evidence, history`;
- три вида записей:
  - `user` — пользователь сообщил или решил сам;
  - `accepted_proposal` — пользователь явно принял предложение ассистента;
  - `assistant_proposal` — предложение ассистента без подтверждения, это НЕ решение;
- проверка цитат в нужных сообщениях и чисел значения;
- запрет предложению ассистента перезаписывать решение пользователя;
- `history` прежних значений, `deleted`, журнал с причинами отклонений;
- отображение фактов с цитатами-источниками.

**Изменено:**
- убраны `locked` и `inherited` — они нужны были только для веток Дня 10;
- проверки вынесены в `rules.py`;
- добавлены два правила слоя: «данные текущей задачи → working» и «вопрос пользователя — не факт».

Тесты Дня 10 на три вида записей перенесены в `tests/test_long_term.py`.

## Правила записи

Модель только **предлагает** операции, записывает их код. Схема операции общая:
`{layer, op: set|delete, key, value, kind, category, evidence, proposal_evidence, reason}`.
В JSON Schema поле `layer` допускает только `working` и `long_term`.

**Short-term**
- Пишет только код, без вызова LLM: пара «сообщение пользователя — ответ ассистента» как есть.
- Только при `status=ok` и `remember=True`. Ошибки API, пустые ответы и контрольные вопросы не пишутся.
- Хранится вся история, окно влияет только на чтение.
- Операция модели с `layer=short_term` отклоняется: «краткосрочную память пишет только код».
- `message_counter` не сбрасывается при очистке. Так номера источников (`source_message`) в LT не совпадут с номерами новых сообщений.

**Working**
- `key` — только поле задачи:
  - `goal`, `deadline`, `budget`, `status`, `next_step` — значение заменяется, прежнее уходит в `history`;
  - `constraints`, `results` — элемент добавляется, дубликат помечается `unchanged`.
- `status` ∈ `planning | in_progress | blocked | done`. Русские синонимы нормализуются («в работе» → `in_progress`).
- Цитата должна быть у пользователя (`user`) или это явное согласие на цитату ассистента (`accepted_proposal`). Числа значения должны быть в исходном тексте.
- `assistant_proposal` отклоняется: «неподтверждённое предложение ассистента — не данные задачи».
- После `status=done` задача не меняется. Новая задача начинается с `goal`, а завершённая уходит в `archived` того же файла.
- **В долговременную память ничего не переносится** — ни автоматически, ни при `done`, ни при очистке. Такого пути в коде нет (`test_working_memory_never_becomes_long_term`).

**Long-term**
- Правила Sticky Facts Дня 10 по `kind`.
- Категории: `name, location, environment, constraint, preference, decision, knowledge, reason, alternative, other`.
- Данные задачи отклоняются: категория или ключ `goal, deadline, budget, status, result, next_step, task, plan…` — «место в рабочей памяти».
- Цитата из вопросительного предложения отклоняется: «вопрос пользователя — не факт».
- `delete` проходит только с причиной и цитатой пользователя. Изменение значения сохраняет прежнее в `history`.

## Правила чтения

| Порядок | Слой | Когда попадает в промпт | Как |
|---|---|---|---|
| 1 | Long-term | есть хотя бы один факт | пара user/model; факты сгруппированы по `kind`, неподтверждённые предложения помечены (`INCLUDE_UNCONFIRMED_PROPOSALS=False` скрывает их), цитаты — при `RENDER_EVIDENCE=True` |
| 2 | Working | есть задача и `status ≠ done` | пара user/model: цель, срок, бюджет, ограничения, результаты, следующий шаг, статус — без цитат |
| 3 | Short-term | `window > 0` | последние N сообщений как обычные реплики; если окно начинается с ответа ассистента, он отбрасывается, чтобы роли чередовались |

Менеджер памяти видит только текущие LT и WM (без журналов), предыдущий ответ ассистента и новое сообщение.
Старые сообщения диалога к нему не попадают.

## Эксперимент

**Единый сценарий** `data/scenario.json` — 15 реплик и 15 заранее написанных ответов (30 сообщений):

| Реплики | Что в них | Ожидаемый слой |
|---|---|---|
| 1–7 | имя, город, macOS, «без Docker», стиль ответов, лимит OpenWeather; pytest (предложил ассистент, пользователь принял); launchd (предложил ассистент, не подтверждено) | long-term |
| 8–12 | цель задачи (недельный отчёт в Markdown), срок 20 ноября, «одна страница», готова `load_rates`, следующий шаг — тесты для `build_report`, бюджет 5 USD | working |
| 13–15 | открыт файл на строке 42, пью кофе, перевод слова forecast — сиюминутное, в память не пишется | short-term (окно 6) |

**Вопросы.** 15 одинаковых вопросов (`questions.json`): 7 к LT (из них 2 про авторство), 5 к WM, 3 к ST.
У каждого в эталоне `expected.json` указан слой. Агенту эталон не передаётся.

**Порядок прогона.**
1. Сценарий проигрывается один раз, на каждую реплику — один вызов менеджера памяти.
2. Проверка перезапуска: новый `MemoryManager` из тех же файлов, содержимое и промпт сравниваются.
3. Для каждого варианта файлы копируются в отдельную папку и загружаются заново (= перезапуск агента). Очищается не больше одного слоя, задаются все 15 вопросов.

**Офлайн-режим** (FakeClient) проверяет логику слоёв без платных запросов:
- `scripted_extractor` отдаёт операции из `data/offline_extraction.json`. Среди них 6 намеренно неверных (`_demo`), чтобы показать отказы правил записи.
- `echo_responder` отвечает текстом контекста. Поэтому «верно» здесь означает «нужный факт реально попал в промпт».
- Токены — детерминированный фейковый счёт (3 на часть + 1 на слово), а не токены Gemini.

### Результаты: Gemini (`gemini-3.5-flash-lite`)

Запуск: `main.py --experiment`, 2026-11-16. Полный отчёт — `results/gemini/report.md`, данные — `results/gemini/experiment.json`.
Файлы слоёв — `results/gemini/state/`.
- Сделано 75 вызовов `generate_content`, ни одного неудачного.
- Фактическая стоимость по тарифу ≈ **$0.022**:
  - обновление памяти — $0.0084 (вход 14 889, выход 1 569 токенов);
  - ответы — $0.0138 за все 4 варианта.

**1. Что менеджер памяти записал сам** (операции модели, без подсказок сценария):

| Слой | Записано |
|---|---|
| Short-term | 30 сообщений; в промпт — последние 6 |
| Working | цель «еженедельный отчёт … в Markdown», срок 20 ноября, ограничение «одна страница», результат «load_rates работает», следующий шаг «тесты для build_report», бюджет 5 долларов, статус `in_progress` |
| Long-term | 7 фактов: имя, город, macOS, «никакого Docker», стиль ответов, лимит OpenWeather 1000/день — `user`; pytest — `accepted_proposal` |

Что получилось правильно:
- **Сиюминутные детали (реплики 13–15) модель не записала** ни в один слой — они остались только в краткосрочной памяти.
- Данные задачи модель сама отправила в working, а не в long-term.
- pytest записан как принятое предложение ассистента, а не как решение пользователя.

Ошибки модели, которые правила записи **не поймали** (отклонённых операций — 0):
- **launchd не записан вообще.** Неподтверждённое предложение ассистента (сообщение 14) модель не вернула как операцию. Правила тут ни при чём: им нечего было проверять.

Цель потом заменилась на правильную (сообщение 15, прежняя осталась в `history`), а статус был выставлен по приветствию.
- **`os = Python` в сообщении 1** («пишу на Python»). В сообщении 3 исправлено на macOS. В промпт уходит `os: macOS (ранее: Python)`.

Все три ошибки смысловые. Цитаты и числа в них настоящие, поэтому проверка источника их пропускает.

### Что доказано, а что осталось вероятностным

**Доказано.** Это детерминированный код, и каждое утверждение проверяется тестами или сохранёнными файлами любого прогона.
- **Слои независимы.** Во всех трёх реальных прогонах и офлайн:
  - очистка меняет ровно один файл (`changed_files`);
  - контрольные вопросы не меняют память (`memory_unchanged_by_questions`);
  - перезапуск восстанавливает содержимое и промпт (`restart_check.ok`).
- **Что именно попадает в промпт.** Это видно по сохранённому `prompt_context_text`: например, launchd есть в промпте v3 при наличии LT и отсутствует в v1, v2 и v3 без LT.
- **Учёт токенов по слоям точен.** Разница промптов между вариантами в точности равна `count_tokens` очищенного слоя во всех трёх прогонах.
- **Правила записи работают как описано.** Отклонены 6 из 6 демонстрационных операций офлайн. В v2 сработал реальный отказ «вопрос — не факт».
- **Нормализация цитат исправила баг схемы без ослабления проверки.**
  - Операция v2 отклонялась старым кодом и принимается новым (регрессионный тест).
  - В v3 реальная операция прошла с пометкой `normalized`, цитата сверена с сообщением 14.
  - Цитата, которой нет у ассистента, по-прежнему отклоняется.
- **Модель заполняет поля цитат по образцу `accepted_proposal`.** Это наблюдалось в обоих прогонах, где она предлагала запись (v2, v3).

**Вероятностно.** Одиночные прогоны модели с температурой по умолчанию — по одному прогону на каждую конфигурацию.
- **Предложит ли менеджер памяти запись про launchd:** v1 — нет, v2 и v3 — да. Вероятно, помогло правило в инструкции, но v1 и v2 различаются ещё и случайностью. Двух удачных прогонов мало, чтобы оценить частоту.
- **Смысловые ошибки записи:** `os = Python`, проект как цель, лишний `next_step`. Они меняются от прогона к прогону, правила их не ловят.
- **Ответы при очищенном слое:**
  - честное «не знаю» — 14 из 15 в v1 и 13 из 15 в v3;
  - Q5 зависит от общих знаний модели (✓ в v2, ✗ в v1 и v3);
  - Q7 без LT угадывается по формулировке вопроса.
- **Итоговые суммы оценок** (42/42/42) складываются из таких случайных сдвигов и сами по себе ничего не доказывают. Для статистики нужны повторные прогоны одной конфигурации — например, 5 запусков по ≈ $0.024.

   - Краткосрочная растёт линейно с окном.
   - Рычаги экономии: `RENDER_EVIDENCE=False`, меньшее `SHORT_TERM_WINDOW`, скрытие неподтверждённых предложений (`INCLUDE_UNCONFIRMED_PROPOSALS=False`).
6. **Окно краткосрочной памяти — отдельная настройка чтения, а не хранения.**
   - При `--window 0` пропадают только ответы на ST-вопросы (тест `test_window_zero_moves_short_term_answers_out`).
   - История при этом остаётся в файле.
7. **Цена памяти** — один дополнительный вызов на каждое сообщение пользователя, как у Sticky Facts в Дне 10. Слои не добавляют вызовов, только токены в промпт.
