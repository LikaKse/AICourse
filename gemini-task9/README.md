# День 9. Context Compression

Агент на Gemini API (`gemini-3.5-flash-lite`, как в gemini-task8), который сжимает историю
диалога: последние сообщения хранит без изменений, а старые заменяет кратким summary.
Полная история при этом сохраняется на диске для анализа.

## Архитектура

| Модуль | Назначение |
|---|---|
| `config.py` | Настройки: модель, `SUMMARY_EVERY = 10`, `KEEP_LAST = 6`, промпты, пути, тарифы |
| `agent.py` | `Agent`: вызовы Gemini, `ask()` (вопрос со сжатым контекстом), `summarize()` (создание/обновление summary), обработка ошибок API |
| `context_manager.py` | `ContextManager`: полная история, summary, активное окно, порог и механизм сжатия, сборка запроса |
| `history_store.py` | `HistoryStore` (полная история) и `SummaryStore` (summary) — **два отдельных JSON-файла**, атомарная запись |
| `token_stats.py` | `TokenCounter` (`count_tokens`), разбор `usage_metadata`, суммы, экономия, расчётная стоимость |
| `experiments.py` | Эксперименты A/B, проверка ответов по эталону, сравнение, Markdown-отчёт |
| `compression_audit.py` | **Офлайн-аудит summary** (без API): сохранённые / потерянные / искажённые детали, авторство предложений, отслеживание по версиям v1…vN |
| `main.py` | CLI: `--dry-run`, `--chat`, `--experiment`, `--compare`, `--report`, `--audit` |
| `utils.py` | Маскировка ключа, атомарная запись JSON, нормализация текста для шаблонов |
| `data/dialogue.json` | Сценарий: 25 реплик пользователя + 25 заранее написанных ответов агента |
| `data/control_questions.json` | 15 контрольных вопросов (без ответов) |
| `data/facts.json` | **Эталон**: 15 фактов, правильные ответы (accept/reject-шаблоны) и цитата-доказательство из диалога для каждого. Агенту и суммаризатору не передаётся |
| `data/summary_details.json` | **Каталог деталей для аудита**: 36 деталей диалога и 8 предложений ассистента, у каждой — цитата из диалога. Модели не передаётся |
| `tests/` | 125 pytest-тестов на фейковом клиенте (`tests/fakes.py`), без расхода API |

От gemini-task8 взяты: клиент с `HttpRetryOptions`, `count_tokens` + `usage_metadata`,
сериализация `types.Content` через `model_dump`, атомарная запись, маскировка ключа, фейковый клиент.
Function Calling (инструменты) убран: для задачи сжатия он не нужен и добавлял бы шум в замеры.

## Как работает сжатие

```
full_history.json: [m0 … m9 | m10 … m19 | m20 … m29 | m30 … m39 | m40 … m49]   ← ничего не удаляется
                    summary v1  summary v2  summary v3  summary v4   активные
summary.json:      {"text": "...", "summarized_upto": 40, "version": 4, "updates": [...]}
активная история = full_history[summarized_upto:]
```

1. После каждой пары «вопрос — ответ» `ContextManager` проверяет порог:
   `len(active) >= KEEP_LAST + SUMMARY_EVERY` (16 сообщений).
2. Сжимаются `active[:-KEEP_LAST]` — 10 самых старых активных сообщений; последние 6 не трогаются.
3. Gemini получает **предыдущее summary + только новые сообщения** и возвращает объединённое summary.
   Системная инструкция суммаризатора требует сохранить дословно имена, города, даты, сроки,
   бюджеты с валютой, числа, ограничения, модели и решения; для изменившихся значений — указать
   итоговое и пометить заменённое.
4. `summarized_upto` сдвигается вперёд — сжатые сообщения выпадают из активной истории,
   но остаются в `full_history.json`. **Полный текст каждой версии summary** (v1, v2, …)
   записывается в `summary.json → updates[].text` и в результаты эксперимента B (`summary_versions`).
5. В обычный запрос уходит: `[summary (user)] + [подтверждение (model)] + активные сообщения + вопрос`.

Гарантии:

- **Нет повторного суммирования**: указатель только растёт, каждый фрагмент `[start, end)` записан
  в `updates`; после сжатия в активной истории 6 сообщений, и следующий вызов ничего не делает.
- **Нет бесконечного сжатия**: не больше одной попытки за вызов и только при достижении порога.
- **Ошибка API при создании summary** не меняет состояние: сообщения остаются активными,
  ответ пользователю всё равно формируется, сжатие повторится при следующем вызове.
- **Перезапуск**: история и summary читаются из `state/` (чат) или `results/state_A|B/`
  (эксперименты); несогласованные файлы (summary покрывает больше сообщений, чем есть) дают понятную ошибку.

Каждый эталонный ответ подтверждён цитатой из конкретного сообщения (`evidence`), это проверяют
`validate_data()` и тесты; для вопроса 15 дополнительно проверяется, что в репликах пользователя
`launchd` не встречается. Для вопроса 2 ответ только про «город для прогноза погоды» **не**
засчитывается: нужен именно факт проживания.

Все факты находятся в первых 40 сообщениях, то есть в B они **все** попадают в сжатую часть
(это проверяет тест). Три факта меняются по ходу диалога — проверяется, что summary хранит
итоговое значение, а не первое.

- **A — без сжатия**: 50 сообщений в контексте; 15 вопросов.
- **B — со сжатием**: те же 50 сообщений проходят через `ContextManager` → 4 вызова суммаризации
  (на 16, 26, 36 и 46 сообщениях); перед вопросами в контексте summary v4 + 10 последних
  сообщений (окно между 6 и 15: последние 6 всегда без изменений); те же 15 вопросов.
- Вопросы задаются **независимо** (`remember=False`): каждый запрос = контекст + один вопрос,
  ответы на прошлые вопросы в контекст не попадают.
- Проверка ответа — регулярные выражения из `data/facts.json` по нормализованному тексту
  (регистр, ё→е, разделители тысяч): ответ верный, если совпал accept-шаблон и ни один reject-шаблон.
  Сырые ответы сохраняются в JSON для ручной проверки.
- Платных вызовов: A — 15, B — 4 (summary) + 15 = 34 вызова `gemini-3.5-flash-lite`.

### Офлайн-аудит сжатия

Контрольные вопросы показывают, что модель *ответила*; аудит показывает, что *осталось в summary*.
`python main.py --audit` читает сохранённый прогон (только чтение, API не вызывается) и сравнивает
summary с каталогом `data/summary_details.json`:

| Статус | Значение |
|---|---|
| ✅ сохранена | признаки детали найдены в summary |
| ❌ потеряна | признаков нет |
| ⚠️ искажена | значение противоречит диалогу (например, прежнее 08:00 без пометки «заменено», а 09:30 нигде нет) |
| — не сжималась | деталь из активного окна, передаётся без сжатия |
| ≠ несравнимо | summary создано на другой версии этого сообщения диалога |

Отдельная таблица проверяет **авторство**: советы ассистента (venv, launchd, структура папок,
`.env`/python-dotenv, …) не должны попадать в summary как решения пользователя. Статусы:
«записано как решение», «без указания автора», «приписано ассистенту», «принято пользователем»
(httpx — пользователь сам сказал «Возьмём httpx»).

Если в прогоне сохранены версии summary, отчёт показывает статус каждой детали в v1…vN и версию,
в которой деталь впервые потерялась или исказилась. Для прогонов до этой доработки версий нет —
отчёт об этом предупреждает. Аудит сверяет сохранённую полную историю прогона с текущим диалогом
и помечает несравнимыми детали из изменённых сообщений. Сам аудит в `results/` не пишет;
`--audit-output PATH` сохраняет отчёт в файл вне `results/`.

Метод эвристический (регулярные выражения): «потеряна» или «записано как решение» — сигнал
проверить строку summary глазами, а не окончательный вердикт.

### Как считаются токены

- `count_tokens` (бесплатно, до отправки): полная история, summary, последние сообщения,
  фактический `contents` каждого запроса. В Gemini Developer API он не учитывает system instruction.
- `usage_metadata` (после ответа): `prompt_token_count` (весь вход с system instruction),
  `candidates_token_count`, `thoughts_token_count`. Для каждого запроса сохраняется разница
  `prompt_token_count − count_tokens`.
- **Экономия на контрольных запросах** — только 15 вопросов A vs B.
- **Общая экономия** — в B добавлены все токены 4 вызовов суммаризации (вход + выход + thinking).
- Стоимость в USD и «точка окупаемости» — **расчёт** по тарифу из `config.PRICING`, а не счёт Google.

### Вывод

Сжатие на 43% сокращает контекст запроса (1 068 → 608 токенов) и на ~40% — вход контрольных запросов; с учётом стоимости
самой суммаризации экономия токенов — 15,73%, а расчётная стоимость при таком коротком диалоге даже выше.
Summary **надёжно сохраняет явные факты и изменения значений** (10/10 основных фактов, все три изменения
значений с пометкой «заменило»), но **теряет причины решений, отвергнутые альтернативы и авторство
предложений** (2/5 дополнительных деталей) — и модель может уверенно ответить неверно, опираясь на такое
summary (вопросы 13 и 15). Чтобы это исправить, можно явно потребовать в промпте суммаризатора сохранять
причины, рассмотренные варианты и кто что предложил — это нужно проверить отдельным прогоном.

## Ограничения метода

- **Один прогон** каждого эксперимента при **temperature 1.0** (значение по умолчанию для Gemini 3) —
  ответы и summary могут отличаться между запусками; для статистики нужно несколько прогонов.
- **Короткий синтетический диалог** (50 сообщений, ≈ 1 тыс. токенов) с заранее написанными ответами
  ассистента: абсолютная экономия мала, а затраты на суммаризацию сравнимы с выигрышем;
  на длинных реальных диалогах соотношение может быть другим.
- **Проверка ответов — регулярные выражения**: засчитывается формулировка, а не обоснованность ответа
  (см. вопрос 2 — верный ответ без опоры на summary). Сырые ответы сохранены для ручной проверки.
- **Аудит деталей эвристический**: каталог из 36 деталей составлен вручную по этому сценарию (детали вне
  каталога аудит не видит), статусы определяются шаблонами; проверка авторства опирается на слова-маркеры
  («используется», «хранятся», «предложил») в отдельных предложениях summary и не является доказательством.
- Summary — пересказ моделью: ошибка может накапливаться при каждом объединении (summary от summary).
- Сжимаются целые сообщения; детали из последних 6–15 сообщений передаются без сжатия и summary не проверяют.
