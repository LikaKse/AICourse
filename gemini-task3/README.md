# Задача №3 (День 3): разные способы рассуждения

Сравнение четырёх способов решения задач при двух уровнях рассуждения модели `gemini-3.5-flash-lite`.
Проект построен по образцу `gemini-task2` (повторы, темп запросов, сохранение после каждого шага,
защита результатов, офлайн-проверки).

## Способы

| Способ | Вызовов API | Что получает модель |
|---|---|---|
| **Direct** | 1 | Только текст задачи и общий формат ответа. Никаких инструкций по рассуждению. |
| **Step-by-step** | 1 | То же + «Решай задачу пошагово. Проверь результат перед ответом.» |
| **Prompt generation** | 2 | Вызов 1: модель составляет эффективный промпт для задачи (ответ — обычный текст, без JSON-схемы; модели запрещено решать задачу). Вызов 2: сгенерированный промпт + задача + формат ответа. |
| **Expert group** | 1 | Три роли — аналитик, инженер, критик — обсуждают задачу, затем модель даёт согласованный ответ. |

> **Expert group — это не три независимые модели.** Все три роли *симулирует одна и та же модель
> в одном вызове*: она по очереди пишет рассуждения от лица аналитика, инженера и критика и сама
> сводит их в итог. Независимости мнений, как у трёх отдельных вызовов или моделей, здесь нет.

## Уровни рассуждения

Для каждого способа: `thinking_level = MINIMAL` и `thinking_level = HIGH`
(`types.ThinkingConfig(thinking_level=...)` из google-genai). `thinking_budget` не используется.
Для Prompt generation оба вызова идут с одним уровнем: MINIMAL/MINIMAL или HIGH/HIGH.

По документации Google `gemini-3.5-flash-lite` поддерживает `minimal, low, medium, high`,
по умолчанию — `minimal`. `max_output_tokens` не задаётся: в него входят токены рассуждений,
и на HIGH ответ обрезался бы (так было в задаче №2).

## Формат ответа и проверка

Финальные вызовы всех четырёх способов получают одну и ту же инструкцию формата и одну и ту же
JSON-схему (`response_mime_type="application/json"`, `response_schema=ApiSolution`):

```json
{"answer": "короткий ответ", "explanation": "краткое объяснение"}
```

Правильность проверяется **только программно** (`validators.py`), самооценка модели не учитывается:

| Задача | Эталон | Проверка |
|---|---|---|
| `math_bat_ball` | 0.05 доллара | все числа ответа, переведённые в доллары («5 центов» → 0.05), равны ровно 0.05 (`Decimal`) |
| `logic_syllogism` | да | есть «да/yes/следует», нет «нет/no/не следует»; «да и нет» — неверно |
| `combinatorics_digits` | 24 | в ответе ровно одно различное число, равное 24 |
| `algorithm_loop` | 14 | в ответе ровно одно различное число, равное 14 |
| `order_logic` | D, A, B, C | последовательность букв A–D совпадает точно; понимает «D → A → B → C», «DABC», кириллические заглавные А, В, С |

Нормализация: нижний регистр, неразрывные пробелы, схлопывание пробелов, пунктуация по краям,
десятичная запятая. Ответ, который не разобрался как JSON или не прошёл схему, считается неверным.

## Файлы

- `config.py` — модель, уровни, способы, темп и повторы, шаблоны промптов.
- `tasks.py` — 5 задач с эталонами и функциями проверки.
- `validators.py` — схема ответа (Pydantic), разбор JSON, нормализация, проверки по задачам.
- `experiment.py` — вызовы API, повторы, сохранение, CLI.
- `summary.py` — метрики и Markdown-отчёт.
- `offline_checks.py` — проверки без сети.
- `results/run_N/` — результаты запуска: `run_meta.json`, `raw_results.json`, `summary.md`
  (и `superseded.json` после `--resume`, если были неудачные решения).

## Запуск

```bash
cd ~/work/AICourse/gemini-task3
export GEMINI_API_KEY="ваш_ключ"           # ключ нигде не печатается и не сохраняется

../venv/bin/python offline_checks.py        # офлайн-проверки, без API
../venv/bin/python experiment.py --dry-run  # план и промпты, без API
../venv/bin/python experiment.py --pilot    # пилот: 1 задача × 4 способа × 2 уровня = 8 решений, 10 вызовов
../venv/bin/python experiment.py --full     # полный эксперимент: 40 решений, 50 вызовов
../venv/bin/python experiment.py --resume run_N   # дописать прерванный/остановленный запуск
```

Без `--pilot`, `--full` или `--resume` скрипт запросов не отправляет. При импорте модулей ничего не запускается.

## Надёжность

- Интервал между началами любых двух запросов ≥ 13 с (бесплатный тариф: 5 запросов в минуту;
  попытки с ошибкой тоже засчитываются).
- Повторы при 503/504/429: не больше 3 попыток на вызов, паузы 15 и 30 с. Для 429 «per minute»
  учитывается подсказка сервера «retry in Ns» (не больше 60 с).
- 429 из-за **дневной** квоты: эксперимент сразу останавливается, продолжение — `--resume run_N`.
- Ошибки API не скрываются: каждая попытка с кодом и текстом ошибки записывается в `calls[].attempts`.
- После каждого решения `raw_results.json` и `summary.md` перезаписываются атомарно
  (временный файл + `os.replace`); Ctrl+C сохраняет всё уже полученное.
- Каждый запуск — новая папка `results/run_N`; существующие не перезаписываются. `--resume`
  не трогает успешные решения; неудачные переносит в `superseded.json` и выполняет заново.
- Отсутствующие поля `usage_metadata` и `finish_reason` записываются как `null`, а не 0.

## Что записывается

Для каждого решения: `task_id`, `strategy`, `thinking_level`, `model`, `prompt`, `generated_prompt`,
`answer`, `explanation`, `expected_answer`, `is_correct`, `check_reason`, `latency_sec`,
`prompt_token_count`, `candidates_token_count`, `thoughts_token_count`, `total_token_count`,
`finish_reason`, `attempts`, `retries`, `api_error`, а в `calls` — метрики каждого вызова отдельно.
Для Prompt generation токены и время — сумма генерации промпта и решения; если у одного из вызовов
нет usage, сумма — нижняя оценка (`tokens_incomplete: true`). Дополнительно отмечается, не содержит
ли сгенерированный промпт эталонный ответ (`generated_prompt_leaks_answer`).

## Результаты и выводы

Полный эксперимент: `results/run_2/` (05.11.2026, `gemini-3.5-flash-lite`, 5 задач × 4 способа × 2 уровня = 40 решений).
Данные проверены финальным аудитом: 40 уникальных решений, все получены без ошибок API, все ответы верны
по программной проверке; таблица ниже пересчитана независимо по `raw_results.json` и совпадает с `summary.md`.

Одно решение (`order_logic | expert_group | HIGH`) в первом проходе завершилось клиентским таймаутом
(`ReadTimeout`, 180 с) и было выполнено заново через `--resume run_2`. Неудачная попытка сохранена
в `superseded.json` и в статистику не входит.

успешным вызовам, без пауз и повторов.

### Основные выводы

1. **Все способы решили все задачи на обоих уровнях — точность 100% во всех 8 комбинациях.**
   Даже Direct при MINIMAL ответил верно 5 из 5. Для `gemini-3.5-flash-lite` эти задачи оказались
   слишком простыми (эффект потолка).
2. **100% точность на пяти простых задачах не позволяет доказать преимущество какой-либо стратегии.**
   На этом наборе нельзя ответить, помогают ли Step-by-step, Prompt generation и Expert group при
   MINIMAL и сохраняется ли их преимущество при HIGH: улучшать было нечего. Различия видны только
   в стоимости.
3. **HIGH дороже MINIMAL в 3,5–5,3 раза по токенам без выигрыша в точности.** Разница почти целиком
   приходится на `thoughts_token_count`. При MINIMAL API не вернул это поле, а `total_token_count`
   равен сумме входных и выходных токенов — то есть отдельно учтённых токенов рассуждения нет.
   Это не означает, что при MINIMAL рассуждение полностью отключено: по документации Google у
   `gemini-3.5-flash-lite` рассуждение включено на минимальном уровне, а по данным API нельзя
   определить, что происходит внутри модели.
4. **Prompt generation — самый дорогой способ.** Он использует **два API-вызова** (генерация промпта
   и решение по нему) и требует в 3,2–3,9 раза больше токенов, чем Direct на том же уровне
   (507 против 130 при MINIMAL, 2 204 против 692 при HIGH). Утечки эталонного ответа в
   сгенерированные промпты не обнаружено (для задачи «да/нет» эвристика не применима).
5. **Step-by-step — самая дешёвая добавка к Direct:** +25% токенов при MINIMAL и +10% при HIGH.
6. **Expert group — это один вызов одной модели, которая симулирует три роли** (аналитик, инженер,
   критик), а не три независимые модели. Стоимость — около 2× от Direct при MINIMAL и 1,4× при HIGH;
   выигрыша в точности на этом наборе нет.

### Токены надёжнее времени

Время ответа зависит от нагрузки на серверы Gemini, а не только от способа и уровня рассуждения.
Во время прогона было 9 временных ошибок 503/504; отдельные ответы шли до 80 с (Direct MINIMAL:
среднее 27,3 с при медиане 13,9 с), и в среднем HIGH оказался даже немного быстрее MINIMAL
(20,1 против 23,2 с). Поэтому для сравнения способов надёжнее токены; время приведено справочно.

### Ограничения эксперимента

- **Мало задач:** по 5 на группу — одна задача меняет точность на 20 п.п.; каждое решение выполнено один раз.
- **Простые задачи:** все решаются уже Direct при MINIMAL, поэтому эффект стратегий не измерим.
- **Задача 5 подсказывает ответ:** в условии люди перечислены в том же порядке, что и в правильном ответе.
- **Одна модель:** результаты относятся только к `gemini-3.5-flash-lite` и могут не переноситься на другие модели.
- **Expert group симулирован:** роли не независимы, это одна модель в одном вызове.
- **Время зашумлено** нагрузкой на сервер и повторами после 503/504.
- **Что стоит сделать дальше:** взять задачи, на которых Direct при MINIMAL ошибается, и повторить
  каждое решение несколько раз — только тогда можно сравнивать точность стратегий.
